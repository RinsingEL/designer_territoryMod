# 旋转模板 pivot 与规划几何错位导致分片裁剪

## 状态

- 状态：代码已修复，自动测试通过，待新未生成区域实机复验。
- 系统：City 固定 NBT 模板 worldgen 落地。
- 现场：`落地测试`，run `city_stubbs_farm_playtest_20260717_01`，city `city_stubbs_farm_test_01`。
- 涉及模板：`geomantia:city/stubbs/commercial/small_butcher_shop_01`，D4 锚点 `660210,659551`，`CLOCKWISE_90`。
- 边界：本案只记录模板旋转坐标与 owner fragment 裁剪不一致；不把 RoadWeaver 道路穿楼风险归因到本案，也不修改当前落地契约或运行时代码。

## 现象

农庄实测中，计划落地的屠夫铺疑似只有局部建筑，视觉上像被道路截断。需要区分三种可能：导出的 NBT 本身不完整、道路在模板落地后覆盖方块、或模板落地时已被裁剪。

## 分层排查与证据

### L0 资源真值

1. 原始 `small_butcher_shop_01.nbt` 的尺寸为 `19 x 8 x 13`，非空气方块 `621` 个，原始非空气范围完整覆盖 `x=0..18`、`y=0..7`、`z=0..12`。
2. 原始模板含多个门方块和完整屋体材料，不是导出时只保存半栋。

### L2 规划几何真值

`CityTemplatePlacementGeometry` 将顺时针 90 度旋转归一化为：

```text
(x, z) -> (depth - 1 - z, x)
```

因此该模板的规划 transformed size 为 `13 x 8 x 19`，D4/D6 在锚点 `660210,659551` 计算的 closed footprint 为：

```text
x=660210..660222
z=659551..659569
```

owner fragment 的 `BoundingBox` 也直接使用上述 planned footprint 的局部范围。

### L3 执行层真值

`MinecraftCityTemplateWorldgenPlacer.WorldGenLevelWriter` 在写入时同时：

1. 将 `StructurePlaceSettings.rotation` 设为顺时针 90 度；
2. 调用 `template.getZeroPositionWithTransform(BlockPos.ZERO, mirror, rotation)`；
3. 将该结果额外设为 `settings.setRotationPivot(pivot)`；
4. 仍以 L2 未偏移的 planned owner fragment 作为 `settings.setBoundingBox(ownerBox)`。

离线读取客户端关闭后已落盘的 `r.1289.1288.mca`，将模板全部非空气方块与保存区块逐点比较：最匹配的实际坐标不是 L2 的归一化映射，而是同一顺时针映射再沿 Z 轴负方向偏移 `12` 格（原始 depth - 1）。对应实际范围为：

```text
x=660210..660222
z=659539..659557
```

它与 L2/D6 planned footprint 的交集只有 `z=659551..659557`，即 19 行深度中仅 7 行仍落在已注册的 owner fragment 内。worldgen 写入受 `ownerBox` 限制，因此模板不是完整写入后再被删除，而是在写入时就被 fragment 裁剪。

### 道路与截图的排除说明

1. 保存区块的 planned butcher footprint 内只发现极少量道路样方块（`cracked_nether_bricks`、`red_nether_bricks` 及 slab 共 5 个），远少于缺失的数百个 NBT 方块，不能解释半栋建筑。
2. 用户在截图前曾手动执行过不同坐标的 `/place template`，因此截图不能单独证明哪一份是 D7 计划副本；本案结论以原始 NBT、D4/D6 坐标和保存区块逐点对比为准。
3. 当前 butcher 的道路入口规划点为 `660216,659565`，位于 planned footprint 内；RoadWeaver bridge 只传 `BlockPos`，未传入口朝向，首段连接可能穿过建筑。这是独立的道路连接设计缺陷，须另案处理，不能代替本案根因。

## 根因确认

根因是 L2 规划几何与 L3 Minecraft 写入变换的锚点语义不一致：前者把旋转结果归一化到锚点为最小角，后者又叠加了 Minecraft 模板的零点变换 pivot。`lockedActualFootprint`、fragment owner 分配和 `BoundingBox` 以 L2 坐标为准，实际写入位置以带 pivot 的坐标为准，二者冲突后由 `BoundingBox` 截去大部分结构。

`template.placeInWorld(...)` 返回成功只能说明该次 fragment 内存在可写内容，不能证明完整 NBT 已位于 D6 locked footprint；因此当前 fragment ledger 也不能作为“旋转模板完整落地”的充分验收依据。

## 已实施修复

1. 保持 City `anchor=transformed footprint minX/minZ` 和 closed footprint 契约不变。worldgen 将 `getZeroPositionWithTransform(anchor, mirror, rotation)` 作为规范化 placement origin，`rotationPivot` 固定为 `BlockPos.ZERO`；不再把 placement origin offset 二次写入 pivot。
2. `CityTemplatePlacementGeometry` 的 mirror 名称同步 Minecraft 原生轴语义：`LEFT_RIGHT` 翻转 Z / NORTH-SOUTH，`FRONT_BACK` 翻转 X / EAST-WEST。局部点、方向、`roadEntrances[]` 和 transformed footprint 使用同一 mirror-first-then-rotation 公式。
3. 新增 runtime transform 适配对象，直接调用 Minecraft `StructureTemplate.transform(..., pivot=ZERO)`，逐个源 X/Z 坐标与 City 规划结果对比，同时校验 transformed footprint 为双射且 min/max 与 anchor 契约一致。
4. worldgen placement request 原样携带 D6 `lockedActualFootprint`；写入前校验 identity footprint、runtime footprint、locked footprint 与 owner fragment。漂移分别返回 `TEMPLATE_RUNTIME_TRANSFORM_MISMATCH` 或 `TEMPLATE_LOCKED_FOOTPRINT_MISMATCH`，writer 不写方块，registry 也拒绝 fragment/completed。
5. owner `BoundingBox` 继续只覆盖当前 owner fragment；跨 owner 合并仍由 Bug 1 已提交的 fragment/datum 事务完成，本修复没有改变其 pending/frozen/FULL retry 语义。

RoadWeaver 外侧 stub、入口朝向传递和首段穿楼仍是独立故障，本修复只保证 transformed entrance 坐标与方向符合模板变换。

- `CityReservationMaskRegistryTemplateFragmentTest` 已覆盖旋转非正方形模板最后一个 owner 才 completed，以及 drift footprint 不产生 fragment/completed。
