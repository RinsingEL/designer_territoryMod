# C1-C4 城市规划过程

> 当前状态提示：本文是旧“城市语法 -> 功能区 -> 道路 / 边界”过程设计，已不作为当前 active path 真值。当前主线不再先生成 `FunctionZoneMap` / `BuildableAreaMap`；请先读 `../案子/README.md` 和 `../案子/D3-D6结构落地驱动城市重构-v0.1/README.md`。

## 定位

C1-C4 是同一个城市规划过程，不作为四个互不相干的小系统开发。它回答的是：一座已经被 T 阶段登记的城市，应该在局部地形上形成怎样的功能区、道路和边界。

C1-C3 只产出规划图层和可验证报告，不放置真实结构。C4/D5 分成计划和执行两步：`city_plan_d5` 仍只生成道路 / 边界 / 缓冲区计划与预览，`city_execute_d5` 在显式确认后才通过 WorldEdit 后端真实修改世界；首版不放置住宅、市场、神庙等功能建筑。

## 总流程

```mermaid
flowchart LR
  A["CitySeed / CitySiteCandidate"] --> B["C1 局部 TerrainPatchMap"]
  B --> C["C2 CityGrammarPlan"]
  C --> D["C3 FunctionZoneMap"]
  D --> E["C4 RoadIntent / BoundaryIntent / BuildOperationPlan"]
  E --> F["CityPlanningPackage"]
  F --> G["StructureLandingIntent"]
```

## C1 局部地貌事实

目标：在城市候选范围内生成比 W 粗扫更细的地貌事实。

输入：

- `CitySiteCandidate`
- 所属 `RealmTerritoryMap`
- GIS 缓存和局部刷新能力

输出：

- `TerrainPatchMap`
- `TerrainPatchSummary`
- `terrain_preview.png`
- `terrain_manifest.json`

约束：

- C1 不决定功能区名称。
- C1 不判断最终建筑可放置性。
- C1 不直接生成城市边界。
- C1 的 step 应由城市规模和机器预算决定，不能沿用 W 粗扫 step 做城市内部规划。

## C2 城市语法

目标：根据国度风格、城市功能类型和局部地貌，确定城市组织方式。

输入：

- `CitySeed`
- `RealmProfile`
- `TerrainPatchSummary`

输出：

- `CityGrammarPlan`

`CityGrammarPlan` 应描述：

- 城市类型，例如新手村、首都、港口城、矿山城、边境要塞、宗教城。
- 功能比例，例如居住、市场、生产、农田、防御、公共空间。
- 组织方式，例如沿河、环广场、贴山麓、沿主路、分散村落、梯田式。
- 边界风格，例如城墙、木栅、水岸、自然林带、台地边缘、道路过渡。
- 道路倾向，例如轴线、环路、枝状、沿岸、山路。

约束：

- AI 可以参与 C2，但它只给策略和比例，不给逐格最终结果。
- 程序必须校验功能比例、规模上限和禁用功能。
- C2 不手填 jigsaw `max_depth`、`radius`、`piece_budget`。

## C3 功能区落图

目标：把 C2 的语法和比例落到局部地图上，生成具名功能区。

输入：

- `TerrainPatchMap`
- `CityGrammarPlan`
- `CitySiteCandidate`
- 所属国度边界和水体、坡度、道路候选线

输出：

- `FunctionZoneMap`
- `zone_summary.json`
- `function_zone_preview.png`

规则：

- 一个地貌 patch 可以拆成多个功能区。
- 多个小 patch 可以合并成一个跨地貌功能区。
- 可重复功能必须支持多实例命名，例如 `东市`、`南市`、`港口鱼市`。
- 功能区需要有面积、容量、连通性和边界质量评分。
- 功能区不应越出城市候选范围或所属国度允许范围。

推荐第一版功能区：

| 类型 | 典型用途 |
| --- | --- |
| `civic_core` | 主广场、村厅、城镇中心。 |
| `residential` | 居住建筑和街坊。 |
| `production` | 工坊、仓储、矿业、伐木等。 |
| `market` | 交易、市集、港口鱼市。 |
| `farm_or_pasture` | 农田、牧场、温室。 |
| `defense` | 城门、岗楼、边境要塞。 |
| `harbor_or_waterfront` | 码头、水岸、渔村。 |
| `sacred_or_cultural` | 神庙、纪念物、学院、仪式空间。 |

## C4 边界与道路

目标：把功能区边界转成真实可消费的对象，并生成道路网络。

输入：

- `FunctionZoneMap`
- `TerrainPatchMap`
- `CityGrammarPlan`

输出：

- `RoadIntent`
- `BoundaryIntent`
- `BuildOperationPlan`
- `city_planning_preview.png`
- `WorldMutationReport`（仅执行后）

D5 两步入口：

- `city_plan_d5` 读取 D3/D4 产物，生成道路、边界、缓冲区和模板 marker 的计划与预览，不修改世界。
- `city_execute_d5` 读取已落盘的 `BuildOperationPlan`，必须传 `confirmWorldMutation=true`，通过 `WorldEditMutationBackend` 执行并输出 `world_mutation_report.json`。

边界处理类型：

- 主路或支路。
- 城墙、栅栏、壕沟。
- 水岸、码头、桥。
- 绿化带、林带、农田缓冲。
- 台阶、坡道、挡墙。
- 软过渡区。

道路要求：

- 城市入口到中心功能区必须连通。
- 主要功能区之间应有至少一条可解释路径。
- 道路不能只是一张线图，必须带宽度、等级、节点、通过性约束和对应的操作引用。
- 山地、水岸、森林城市可以有不同道路形态，但都要能被结构落地层消费。

## 质量门

`CityPlanningPackage` 进入结构落地前至少满足：

| 检查 | 通过口径 |
| --- | --- |
| 候选合法性 | 城市中心、核心区和主要功能区不越出所属国度允许范围。 |
| 地貌可解释 | 功能区选择能回溯到地貌、国度偏好或城市功能类型。 |
| 比例合理 | 功能区面积比例符合 `CityGrammarPlan`，允许小幅偏差。 |
| 连通性 | 中心区、入口和主要功能区连通。 |
| 多实例 | 市场、居住、生产等可重复功能不被硬编码成唯一实例。 |
| 可物化 | 每个需要结构落地的功能区都能输出边界、道路接入点和 anchor 需求。 |

## 人工 Review 重点

- 城市是否和所在国度风格一致。
- 功能区是否只是地貌颜色换名。
- 道路是否真的服务城市，而不是随机连线。
- 水岸、山麓、边境等特色位置是否被利用。
- 城市规模是否符合 `CitySeed`，没有因为候选区大就无限膨胀。
