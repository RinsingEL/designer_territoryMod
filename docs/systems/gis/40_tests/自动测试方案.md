# GIS 自动测试方案

本文定义 GIS 首版给开发 agent 使用的自动测试路径。目标不是替代人工看图验收，而是让 agent 能在实现过程中快速判断：数据结构、指标计算、半径刷新、预览导出和固定存档集成是否破坏。

## 测试目标

- agent 能用命令自动跑完核心 GIS 测试。
- 测试结果能输出机器可读报告。
- 固定 seed、固定存档、固定中心点下的结果可重复。
- 预览图和 progress 图可作为人工复查证据。
- 自动测试不要求每个 Cell 像素级完全锁死，优先验证摘要、状态和边界。

## 测试分层

| 层级 | 运行环境 | 目标 | 推荐频率 |
| --- | --- | --- | --- |
| JVM 单元测试 | Gradle test | 数据结构、状态机、坐标换算、枚举 fallback。 | 每次提交前。 |
| 人造网格算法测试 | Gradle test | 用固定高度矩阵验证坡度、TPI、地貌分类和 Patch 合并。 | 每次改指标或分类规则。 |
| Forge 固定存档集成测试 | Gradle runGameTestServer 或 runClient 自动命令 | 在真实 MC 世界中刷新 GIS、导出 manifest、progress 和预览图。 | 每次改采样、刷新、缓存、预览输出。 |

## Forge 快速启动基础

实现仓库当前 ForgeGradle 已配置这些运行入口：

| Gradle 入口 | 用途 |
| --- | --- |
| `./gradlew.bat test` | 运行普通 JVM 单元测试。 |
| `./gradlew.bat runGameTestServer` | 运行 Forge GameTest 服务端，适合自动化集成测试。 |
| `./gradlew.bat runServer` | 运行无 GUI 服务端，可用于后续脚本化测试。 |
| `./gradlew.bat runClient` | 运行客户端，适合人工看图和调试命令。 |

Forge 运行工作目录为实现仓库的 `run/`，固定存档应放在：

```text
E:\Mod_Dev\StructureBinder\run\saves\
```

如果需要保留多个测试世界，建议命名：

```text
run/saves/gis_plain
run/saves/gis_mountain
run/saves/gis_water
run/saves/gis_mixed
```

## 固定样例配置

首版建议维护一份机器可读样例清单，后续可放入实现仓库测试资源或 config：

```json
{
  "cases": [
    {
      "id": "plain",
      "save": "gis_plain",
      "dimension": "minecraft:overworld",
      "center": [0, 0],
      "radiusChunks": 8,
      "expected": {
        "landformDominant": "plain",
        "unknownMaxRatio": 0.05,
        "failedCellCount": 0
      }
    },
    {
      "id": "mountain",
      "save": "gis_mountain",
      "dimension": "minecraft:overworld",
      "center": [0, 0],
      "radiusChunks": 8,
      "expected": {
        "mustContain": ["ridge", "valley", "slope"],
        "unknownMaxRatio": 0.10,
        "failedCellCount": 0
      }
    }
  ]
}
```

## 自动测试命令目标

首版实现可以先提供调试命令，再由 GameTest 或脚本调用：

```text
/geomantia gis test_run <caseId>
/geomantia gis refresh <radiusChunks>
/geomantia gis progress
/geomantia gis export_preview
```

`test_run` 应自动完成：

1. 读取固定 case。
2. 创建 RefreshJob。
3. 等待任务完成或超时。
4. 导出 progress 最终图、PreviewManifest、统计摘要。
5. 对 expected 做自动断言。
6. 写出测试报告。

## 输出目录

建议所有 GIS 自动测试产物写入：

```text
run/gis_debug/<runId>/
  progress.png
  progress_manifest.json
  preview/
    elevation.png
    slope.png
    tpiSmall.png
    tpiLarge.png
    landform.png
    buildability.png
    preview_manifest.json
  test_report.json
```

`test_report.json` 至少包含：

| 字段 | 说明 |
| --- | --- |
| runId | 本次测试运行标识。 |
| caseId | 固定样例标识。 |
| command | 触发命令。 |
| passed | 是否通过自动断言。 |
| durationMs | 总耗时。 |
| cellCounts | Cell 状态统计。 |
| landformCounts | 地貌类型统计。 |
| patchCounts | Patch 数量和面积摘要。 |
| failures | 失败断言列表。 |
| artifacts | progress、preview、manifest 路径。 |

## 自动断言建议

首版自动断言不要锁死每个 Cell，而是使用摘要约束：

- `failedCellCount = 0`
- `unknownRatio <= 阈值`
- `edgeDirty` 主要集中在依赖边界。
- 固定样例必须包含指定 `LandformType`。
- 主导地貌类型占比在合理范围内。
- Patch 数量不为 0。
- 最大 Patch 面积不小于样例阈值。
- `PreviewManifest` 存在且图层齐全。
- `progress_manifest.json` 最终状态为 completed 或 failed。

## 人工验收边界

自动测试负责证明“系统没有坏、状态没有乱、结果在统计上合理”。地貌是否好看、阈值是否自然、山脊谷地是否符合人的直觉，仍需要人工看预览图判断。
