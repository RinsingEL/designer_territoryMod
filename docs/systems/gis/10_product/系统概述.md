# GIS 系统概述

GIS 是 Geomantia 的地貌基础设施层。它负责把 Minecraft 世界转换成可查询、可缓存、可验证的地理空间事实，再交给城市、道路、国度边界、结构分布等规划系统消费。

GIS 不直接生成城市，也不直接放置结构。它回答的是：某个范围内的地形是什么，哪里平缓，哪里临水，哪里是山脊、谷地、盆地、台地或岸线，哪些区域适合承载后续规划。

## 定位

- 独立于 `city`、`roads`、`realm`、`structure` 的基础系统。
- 面向 Minecraft 世界的区域级地貌认知层，而不是传统 GIS 的完整复刻。
- 以缓存和增量刷新为核心，避免每次规划都重新扫描大量区块。
- 以可视化调试和验收图为重要产物，保证地貌判断可以被人工检查。

## 要解决的问题

- 原版结构和整合包结构常以近似随机的方式散落，缺少对地形地貌、道路联系和区域秩序的理解。
- 城市选址、道路连接、结构群落分布需要共享同一份地形事实，不能各自重复扫描和各自猜测。
- Minecraft 世界数据是区块化、延迟加载、运行时变化的，规划系统需要一个稳定的中间层。

## 不解决的问题

- 不在 MVP 阶段实现真实水文流域、沉积模拟、曲率分析或完整 geomorphon 分类。
- 不负责最终城市分区、建筑放置、道路几何求解。
- 不把主数据保存为人工维护 JSON。JSON 只用于配置、调试摘要和验收输出。
- 不强制一次性构建全世界 Atlas。首版以玩家或规划中心为核心，按半径逐步刷新。

## 核心对象

| 对象 | 职责 |
| --- | --- |
| Atlas Cell | GIS 的最小栅格单元。默认代表若干方块范围，例如 4x4 block，用于承载高度、水、坡度、TPI、地貌分类等字段。 |
| Atlas Region | Atlas Cell 的区域容器。通常按固定区块范围切分，用于缓存、持久化、脏区重算和调试导出。 |
| GIS 指标层 | 从基础采样派生出的数值层，包括坡度、局部起伏、粗糙度、TPI、水距、可建性等。 |
| Landform Patch | 相邻且地貌类型相近的 Cell 合并后的地貌区，供城市、道路和结构系统使用。 |
| Refresh Job | 一次 GIS 刷新任务，描述中心点、半径、预算、依赖边界、执行进度和输出状态。 |
| Preview Manifest | 调试预览图的清单，记录本次导出的图层、范围、版本和生成状态。 |

## 主流程

```mermaid
flowchart LR
  A["刷新请求<br/>中心点 + 半径"] --> B["划分 Atlas Region"]
  B --> C["采样基础层<br/>高度/水/生物群系"]
  C --> D["计算指标层<br/>坡度/TPI/起伏/水距"]
  D --> E["逐 Cell 地貌分类"]
  E --> F["合并 Landform Patch"]
  F --> G["写入缓存与调试输出"]
  G --> H["供城市/道路/国度/结构消费"]
```

## MVP 范围

首版只做能够支撑选址和结构分布的地貌基础层：

- 半径刷新：围绕中心区块按环向外刷新。
- Atlas Cell：默认以固定步长采样，不逐方块扫描整片区域。
- 基础层：高度、水体、生物群系、表面方块粗分类。
- 指标层：坡度、局部起伏、粗糙度、小尺度 TPI、大尺度 TPI、水距、可建性。
- 分类层：平原、缓坡、陡坡、山脊、谷地、盆地、台地、岸线、水域等基础地貌。
- 地貌区：把相邻 Cell 合并成可被规划系统消费的 Patch。
- 调试图：输出高度、坡度、TPI、地貌分类、可建性等预览图。

## 消费者

| 系统 | 使用 GIS 的方式 |
| --- | --- |
| City | 读取可建性、地貌区、坡度、水距，决定城市候选点和城区范围。 |
| Roads | 读取坡度、障碍、水体、山脊和谷地，计算更自然的连接代价。 |
| Realm | 读取山脉、水系、海岸和地貌区，辅助区域边界与势力范围。 |
| Structure | 读取地貌标签和可建性，让结构群落更像是“属于这个地方”。 |
| Debug Tools | 读取 Atlas 和 Patch，渲染预览图、覆盖层和验收报告。 |

## 设计原则

1. 先区域级，再精细化。GIS 先帮助系统理解大地貌，再让城市或道路局部细化。
2. 先缓存事实，再消费事实。规划系统不应直接重复扫描 Minecraft 世界。
3. 先可解释，再自动化。每个地貌判断都应该能被预览图和字段追溯。
4. 先 MVP 指标，再扩展复杂地理模型。不要在首版引入难以验收的大模型。
