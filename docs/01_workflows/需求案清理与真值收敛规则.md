# 需求案清理与真值收敛规则

## 用途

本规则用于防止快速迭代留下的旧需求案、部分覆盖案和错误 AI 总结继续影响需求定位与实现。工作树只保存当前仍有效、可直接用于开发与验收的需求真值；完整历史由 Git 保存，不在工作树建立历史案或 archive 副本。

## Session 到期检查

每次进入 session 时，在开始读取需求案、搜索代码或修改文件前，只运行一次：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File E:\Mod_Dev\StructureBinder\scripts\check_requirement_cleanup_due.ps1
```

该脚本只读取 `E:\Mod_Dev\StructureBinder\run\workflow_state\requirement_case_cleanup.json` 并输出一行 `OK` 或 `DUE`，不得扫描案子、统计文件数量、读取导航或加载本规则正文。

- 默认检查周期为 1 天；状态文件中的 `intervalDays` 可调整周期。
- 状态文件缺失、无效、`lastCompletedAt` 为空、`status` 不是 `CLEAN`，或当前时间不早于 `nextCheckAt` 时，本次检查视为到期。
- 输出 `OK` 时立即继续用户当前任务，*MUST NOT* 读取本规则正文、案子索引或任何需求案，不增加报告。
- 检查到期时先询问用户是否现在开始需求案清理；用户未同意时继续当前任务，不得擅自展开案子审计。
- 用户同意后暂停当前任务，先完整执行本规则；清理完成后恢复原任务。暂停不扩大原任务授权，也不得丢弃原任务进度。
- 只有完整完成一次审计、必要清理和验证后，才更新 `lastCompletedAt` 与 `nextCheckAt`；拒绝、跳过或中途停止不得伪装成已完成。
- 新建替代案、修改职责链归属、把设计稿提升为实现依据，或发现同一职责链存在相反要求时，立即把状态设为 `DUE_REQUIREMENT_CHANGED`；这类事件不等待下一天。普通文字修订和不同职责链并行工作不触发清理。

## 锁定当前真值

仓库可以同时保存和推进多个案子，唯一性只在同一职责链内判断，不对整个仓库设置唯一案子。用户当轮明确指定的需求案路径和最新确认原话是本次任务最高真值。用户未指定路径时，只从目标 system / tool README 与案子索引定位本次任务所属职责链。

每条职责链使用以下身份区分并行状态：

- `实现当前案`：该职责链当前代码开发和验收的唯一需求依据，每条职责链必须且只能有一份。
- `设计中案`：尚在讨论或尚未接管实现，可以有多份，不得自动参与当前代码解释和验收。
- `能力参考`：跨案复用的稳定能力说明，不决定所属职责链的整体流程顺序。

不同职责链可以同时开发或设计；同一职责链也可以一边维护实现当前案、一边设计下一案。只有用户明确要求下一案接管实现时，才将其提升为 `实现当前案`，原实现当前案进入本工作流完成迁移和删除。不得根据文件修改时间、文件名中的“最新”、目录顺序或案子数量自动认定当前案。

一旦锁定当前案，普通开发不得再通过全目录关键词搜索读取其他产品案。只有用户要求追溯、发现明确冲突，或正在执行本清理工作流时，才读取与当前案职责直接重叠的旧案。不得用旧案、Git 历史、开发记录、现有代码或测试覆盖当前案和用户最新原话。

如果索引无法唯一定位本次职责链的实现当前案，停止实现并进入本工作流的审计阶段，不得自行挑选看似相关的案子继续开发。

## 审计与收敛

只审计与当前案职责重叠的文件，不默认遍历无关领域。对每份重叠旧案按以下结果处理：

- 仍有效且当前案缺失的用户确认内容：迁入当前案，保持需求案固定结构。
- 已被当前案覆盖或与最新原话冲突的内容：不迁移，删除旧案。
- 与当前案完全重复的内容：删除重复案。
- 仍是独立、有效能力的内容：保留，但从流程需求案改为职责明确的独立入口，不得继续与当前案争夺同一流程真值。
- 无法从用户原话判断是否仍有效的内容：列出冲突并询问用户，不得由 AI 猜测。

不得保留“部分内容被覆盖”的混合案。仍有效部分必须迁出，剩余旧案随后删除。不得为了方便追溯在当前目录、隐藏目录或 archive 中复制已废弃 Markdown；需要历史时读取 Git。

## 删除与工作区保护

用户同意启动本次清理后，删除当前清理范围内已经提交、且工作区没有未提交修改的旧文件，无需再次逐项请求授权。

删除前必须用 Git 确认文件已跟踪并检查工作区状态：

- 已提交且干净的旧文件可以直接删除。
- 存在未提交修改的跟踪文件不得删除或覆盖，先从清理范围排除并报告。
- 未跟踪文件不得作为旧案擅自删除。
- 当前案、稳定契约、测试入口、代码入口和用户未放入清理范围的文件不得因关键词相似被删除。

清理开始时输出简短映射，至少说明旧案路径、保留或迁移内容、删除理由和当前真值入口。该映射用于 review，不是额外审批门；只有发现语义无法判断或未提交内容冲突时才停下询问。

## 更新入口

完成迁移和删除时同步更新当前职责链直接相关的 system / tool README 与案子索引：

- 每条职责链的 `实现当前案` 入口必须唯一；不同职责链的当前案可以并存。
- 删除已废弃案的链接、状态和说明。
- 用 `实现当前案|设计中案|能力参考` 标记职责，不再使用没有职责链含义的“最新需求案”。
- 不得继续使用“部分覆盖”“旧流程仍开发中”等需要读者自行拼接真值的状态。

工作流规则只保存清理行为；用户需求仍写入需求案，字段写入契约，开发过程写入实现仓库任务记录。

## 验证与留档

清理后至少完成以下验证：

1. 检查目标职责链只剩一个 `实现当前案` 入口，其他职责链和设计中案未被误删。
2. 搜索被删除案名和路径，清除失效引用。
3. 检查当前案没有丢失仍有效的用户原话和示意图。
4. 检查工作区 diff，确认未修改无关文件、未覆盖已有改动。
5. 按开发与 Bug 留档规则更新工作流任务记录；提交仍需用户明确授权。

历史 review 使用 Git 的提交、diff、tag 或以后提供的只读历史查询工具。历史查询只在用户明确要求时进行，不把旧案恢复到当前工作树。
