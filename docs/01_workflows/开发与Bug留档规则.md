# 开发与 Bug 留档规则

## 用途

本规则用于让以后遇到相同或相似问题时，能够快速找到以前的现象、根因、修改方式和验证证据，避免重复排查和重复踩坑。

所有实现开发和 Bug 都必须留下可追溯记录。开发记录保存本次实际改动及验证，Bug 记录保存可复用的问题经验。它们服务于后续参考、接手、复查和提交，不作为当前需求、契约或实现真值，也不默认进入无关任务的 AI 上下文。

## 开发记录

凡修改实现代码、配置、测试、MCP 工具或项目工作流，都在开始修改时创建或继续使用一份任务记录：

```text
dev_docs/systems/<系统>/active/YYYYMMDD_中文任务名/任务记录.md
dev_docs/tools/<工具>/active/YYYYMMDD_中文任务名/任务记录.md
dev_docs/workflows/<主题>/active/YYYYMMDD_中文任务名/任务记录.md
```

固定使用简短结构：

```markdown
# 任务名称

*需求入口*：需求案、用户原话或对应任务。

*修改内容*：实际改变的模块和行为。

*验证结果*：执行的验证及结果。

*剩余问题*：没有则写“无”。
```

同一任务只维护一份记录。不要粘贴大段命令输出、源码、完整 diff 或重复需求案。

## Bug 记录

发现实现缺陷时立即在对应系统、工具或工作流的 `故障索引.md` 登记。根因尚未确认时标记为“待定位”，不得把推测写成结论。

每条 Bug 至少记录：

```markdown
*现象*：玩家、Agent 或测试实际看到什么。

*首次偏离*：最早从哪一步开始错误。

*根因*：待定位或最终确认原因。

*修复*：尚未修复或实际修改内容。

*验证*：尚未验证或证明修复的入口与结果。

*记录*：任务记录与提交。
```

故障索引只保留摘要和链接，详细过程写入对应任务记录。Agent 自身命令或参数错误记录在 Agent Loop 调用记录中，不登记为产品 Bug。

## 归档

任务未提交时保留在 `active/`。提交成功后，将任务目录移动到同领域：

```text
archive/<短提交号>_vX.Y.Z_中文标题/
```

只在继续同一任务、发生交接或排查相关 Bug 时读取任务记录；普通开发不得默认加载历史记录。

## 哪些留档进入 Git

实现仓 `.gitignore` 已按以下规则配置，无需手动 `git add -f`：

- `active/` 下进行中的任务记录只留在本机；
- `archive/*/任务记录.md` 与各处 `故障索引.md` 自动纳入版本管理；
- 日志、截图、压缩包等其他证据默认忽略，确需随归档保存时显式 `git add -f`；需要保存哪些，见下一节。

## 验收证据放哪里

2026-10-18 用户确认：验收证据要能让用户、总设计师和其他 agent 在仓库里直接看到，不能只存在某一台电脑上。

| 证据 | 放哪里 | 要求 |
| --- | --- | --- |
| 关键截图 | 对应任务的归档目录，例如 `archive/<短提交号>_…/evidence/`，用 `git add -f` 纳入 | 每轮挑 2～5 张能说明问题的图：修复前后对比、用户标注的问题位置、最终效果；单张压缩到约 500 KB 以内，文件名写明内容 |
| 小型证据数据 | 同上 | 坐标对比、逐列扫描、结果摘要等 JSON 或文本，单个文件一般不超过约 1 MB |
| 存档、jar、完整证据目录、原图 | GitHub Release 附件 | 仓库里只放上传清单：文件名、大小、SHA-256 和下载地址。做法参照实现仓 `addons/realmfolk/docs/acceptance/20261017/` |
| 启动脚本、本机实例、运行日志全文 | 不入仓库 | 依赖本机路径与环境；任务记录里写明在哪台机器、哪个目录即可 |

- **任务记录和文档里不写本机绝对路径的链接**，例如 `E:/Mod_Dev/...`；这类链接在 GitHub 和其他机器上都打不开。仓库内文件用相对路径链接，Release 文件用下载地址链接；只存在本机的东西写成普通文字说明，不做成链接。
- 截图要能对上结论：在任务记录里写明拍摄位置（坐标）和想说明的问题。
- 旧记录不要求一次性回头改；继续同一任务或排查相关问题时，顺手补上该轮的关键截图并修正路径。
