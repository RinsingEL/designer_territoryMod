# 代码导览编写规范

## 定位

`30_code_guide/` 是方案、契约和实现代码之间的桥。它不是逐行代码注释，也不是产品方案复述，而是用来回答：

- 这个能力在代码里由哪些入口、类和模块承载。
- 一条业务流程在代码中如何推进状态。
- 每一步读取什么、写入什么、禁止产生什么副作用。
- 人工 review 时应重点看哪些风险。
- 测试和验收证据应从哪里取得。

当用户需要 review 过程、agent 需要改流程式代码、或实现代码与方案契约发生偏差时，`30_code_guide/` 应能让读者不用重新反推整条调用链。

## 与其他文档的分工

| 文档层 | 回答的问题 | 不应承担 |
| --- | --- | --- |
| `10_product/` | 为什么做、做什么、边界和阶段职责是什么。 | 不写具体类名和代码调用细节。 |
| `20_contracts/` | 数据结构、字段、接口、状态、配置如何约定。 | 不解释完整业务流程实现。 |
| `30_code_guide/` | 方案和契约如何落到代码，如何修改和 review。 | 不重新定义产品目标或字段真值。 |
| `40_tests/` | 如何证明实现没坏，验收入口和报告在哪里。 | 不替代代码流程说明。 |
| 实现仓库 `dev_docs/` | 过程记录、失败诊断、提交归档依据。 | 不作为当前功能真值。 |

## 推荐目录结构

系统或工具的 `30_code_guide/` 可以分文件夹，但入口必须清晰。

```text
30_code_guide/
  代码导览.md
  flows/
    <流程名>实现指南.md
  review/
    <流程名>Review清单.md
  diagrams/
    <流程名>设计Review流程图.md
    <流程名>代码流程图.md
```

小系统可以只保留 `代码导览.md` 和 1 个流程文件；流程较多时再拆 `flows/`、`review/`、`diagrams/`。不要为单个微小类单独建文件，除非它是独立入口或高风险算法。

## 入口页要求

`代码导览.md` 是索引页，必须短而准，优先回答“去哪看”。

建议包含：

- 当前实现仓库路径。
- 包结构和模块职责。
- 关键入口：命令、MCP、HTTP、事件、任务调度、测试入口。
- 主要类到文档的映射。
- 主流程文件列表。
- 设计 Review 流程图入口：用于人工确认整体过程设计。
- 代码流程图入口：用于 agent 或开发者定位具体调用链。
- Review 清单入口。
- 当前未实现或暂不纳入范围的代码边界。

不建议在入口页塞完整流程细节。入口页太长时，应把流程 walkthrough 移到 `flows/`。

## 流程实现指南要求

流程实现指南用于解释“这条流程在代码里怎么跑”。每个流程文件建议使用同一套结构：

```text
# <流程名>实现指南

## 适用范围
## 入口与触发方式
## 前置条件
## 主调用链
## 步骤明细
## 状态推进
## 读写边界
## 失败处理
## 调试与产物
## 测试锚点
## 常见改动路径
```

### 步骤明细

每一步应尽量用固定字段描述，方便 review：

| 字段 | 写法 |
| --- | --- |
| 目标 | 这一步解决什么问题。 |
| 输入 | 来自哪个契约、对象或上一步结果。 |
| 输出 | 产出哪个对象、状态或文件。 |
| 允许读 | 允许读取的模块和数据。 |
| 允许写 | 允许修改的对象、字段、flag 或产物。 |
| 禁止事项 | 不应触发的副作用、跨层访问或 fallback。 |
| 失败处理 | 抛错、状态标记、日志、报告如何暴露。 |
| 测试锚点 | 哪个单测、集成测试、MCP 工具或 debug 产物能证明它。 |

如果某一步非常简单，可以合并描述；如果某一步跨模块或高风险，必须展开。

## Review 清单要求

Review 清单用于服务人工看 PR 或验收过程。它不是测试清单的重复，而是帮 reviewer 判断“这段代码有没有越界”。

建议按流程步骤组织：

```text
## <步骤名>

- 输入是否来自契约允许的来源。
- 输出是否只写本步骤负责的对象。
- 状态 flag 是否按顺序推进。
- 是否绕过了主流程或复制了业务逻辑。
- 是否产生了未记录的副作用。
- 失败是否能被测试、日志或报告看到。
- 本次改动需要看的测试或产物。
```

Review 清单必须包含高风险点，例如：

- 状态被提前标记为完成。
- 入口层重复实现业务逻辑。
- 调试逻辑进入生产主链。
- fallback 变成默认路径。
- preview 图或报告与契约对象不一致。
- 新字段只改代码没改契约。

## 流程图规则

流程图应服务理解和 review，不追求装饰。不要把所有节点都画成同一种气泡节点，也不要把所有问题都塞进同一张图。

### 图的类型

`diagrams/` 中推荐区分两类图：

| 图类型 | 主要读者 | 回答的问题 | 写法重点 |
| --- | --- | --- | --- |
| 设计 Review 流程图 | 用户、策划、reviewer | 整体过程设计是否正确，阶段责任是否越界。 | 以中文过程节点为主，按产品阶段或验收阶段分组，突出输入、产物、旁路和未来边界。 |
| 代码流程图 | agent、开发者 | 实现调用链从哪里进、经过哪些类、如何落到对象和产物。 | 可以写类名、方法名、包名和具体入口，保持能回到代码定位。 |

设计 Review 流程图不应变成类图或方法调用图；代码流程图也不应代替产品阶段图。两者可以引用同一批契约对象，但服务的 review 问题不同。

### 语言规则

- 过程、动作、判断和阶段节点优先写中文，方便人工 review 一眼看出“这一步在做什么”。
- 数据结构、契约对象、报告文件、接口名和工具名保留真实英文名，例如 `AtlasCell`、`AtlasRegion`、`RefreshJob`、`LandformPatch`、`PreviewManifest`、MCP tool 名、HTTP path。
- 类名、方法名和包名主要放在代码流程图中；设计 Review 流程图只有在必须绑定实现入口时才少量出现。
- 阶段名可以采用“阶段编号 + 中文名”，例如 `G1 基础采样`、`G4 半径刷新与缓存`。阶段编号必须沿用对应系统或工具的产品真值，不另起一套含义。

### 分组规则

存在明确阶段、G 编号或验收过程时，大型流程图应使用 `subgraph` 分组。分组优先来自 `10_product/` 的开发计划、阶段职责或验收范围，例如采样、指标层、分类、刷新、调试预览、自动验收。

箭头表达运行时数据流、控制流或验收流。若阶段编号不等于严格调用顺序，必须在图前或图后说明读图口径，避免把阶段计划误读成执行时序。

未来规划、暂不纳入范围、临时代码和调试旁路要用样式或文字显式标注；不要让 reader 误以为它们已经进入生产主链。

### 视觉语法

推荐视觉语法：

| 类型 | Mermaid 建议 | 用途 |
| --- | --- | --- |
| 入口 | 圆角节点 | 命令、MCP、事件、外部调用。 |
| 处理步骤 | 普通矩形 | 纯计算或流程推进。 |
| 判断 | 菱形 | 分支、可选路径、错误条件。 |
| 数据对象 | 圆柱或带标签节点 | cache、snapshot、manifest、契约对象。 |
| 调试旁路 | 虚线 | preview、日志、报告、临时工具。 |
| 外部消费者 | 分组或不同颜色 | city、roads、realm、structure 等下游。 |

图中必须区分：

- 主链路和调试旁路。
- 数据对象和处理步骤。
- 必选路径和可选路径。
- 当前已实现路径和未来规划路径。

节点文本保持短句，详细说明写在图后。图后应补一小段“读图口径”，说明阶段来源、箭头含义、旁路边界和本图不回答的问题。

## 引用代码的规则

- 使用类名、包名、方法名定位实现入口。
- 可以引用实现仓库绝对路径，但不要把文档变成代码快照。
- 不复制大段代码；只描述职责、输入输出和关键调用关系。
- 如果代码和文档不一致，应明确冲突点，并判断是修代码还是修文档。
- 临时代码必须标注临时性、启用条件和移除条件。

## 更新触发

出现以下情况时必须检查并更新 `30_code_guide/`：

- 新增或移动核心入口类。
- 改变主调用链、状态推进顺序或模块职责。
- 新增 MCP/HTTP/命令/事件入口。
- 修改数据契约字段、状态枚举或配置表，并影响代码读写方式。
- 新增流程式能力，例如刷新、导入、生成、扫描、求解、放置。
- 新增调试预览、报告、snapshot 或复现入口。
- 新增或调整阶段编号、G 阶段、验收阶段或流程图分组方式。
- 用户明确表示需要更方便 review 代码过程。

## 常见反模式

- 只有包结构表，没有流程 walkthrough。
- 只写“某模块负责某事”，不写输入、输出和状态变化。
- 把产品方案复制到 code guide，导致方案和实现说明混在一起。
- 流程图全是同一种节点，看不出主链、旁路和数据对象。
- 设计 Review 流程图塞满类名和方法名，导致用户无法 review 过程设计。
- 阶段图另起编号或含义，和 `10_product/` 的开发计划冲突。
- Review 清单只写“测试通过”，没有越界和副作用检查。
- 文档只告诉 agent 改哪里，不告诉用户该 review 什么。
- 把历史失败过程写进 code guide；这类内容应放 `dev_docs/` 或故障索引。

## 最小完成标准

一份合格的 `30_code_guide/` 至少应满足：

1. 能从入口页找到主要代码类和流程文件。
2. 至少一条主流程有实现指南。
3. 主流程的每个关键步骤有输入、输出、允许写和测试锚点。
4. 有一份可用于人工 review 的清单。
5. 流程图能区分主链路、数据对象和调试旁路；如存在阶段化验收，应有面向人工 review 的阶段流程图。
6. 文档不重新定义 `10_product/` 和 `20_contracts/` 已经定义的真值。
