# 开发流程

从一个想法到进入游戏的完整链路。各步骤的细则在对应工作流和规范里，本页只串联顺序；状态统一记录在[路线图](路线图.md)。

```mermaid
flowchart TD
  A[用户提出想法] --> B[写设计中案<br/>原话 + AI 总结]
  B --> C{用户确认接管实现？}
  C -->|否，继续讨论| B
  C -->|是| D[设计中案提升为实现当前案<br/>路线图：已接管]
  D --> E[实现仓任务记录 active/<br/>必要时写契约]
  E --> F[开发 + 自动测试<br/>云端可运行 gradle 测试]
  F --> G[功能分支提 PR，目标主线分支]
  G --> H[用户本机真实游玩验收]
  H -->|有问题| E
  H -->|通过| I[合并 PR，任务记录归档]
  I --> J[路线图：完成；凑齐里程碑时升版本]
```

## 分支

- 两个仓库当前的主线分支都是 `codex/offline-structure-studio`，代表最新的已合并状态。GitHub 上的 `master`（实现仓）与 `main`（文档仓）是 LFS 迁移前后分叉的旧历史，与主线没有共同祖先；如何处理待用户决定，决定前不要以它们为基线。
- 每项工作在独立的功能分支上进行，完成后提 PR 合入主线分支；双仓库联动时两边各提一个 PR，在描述中互相链接。
- 设计中案、规则整理等纯文档改动同样走 PR，便于用户集中审阅。
