# 配置、生成与程序接入 · 拟议接口

回到[总入口](README.md)。以下接口**没有现有程序支持**；正式人口契约和 design.json v2 继续使用原字段。可以审查或修改本草案，但不能把样例复制进当前 config/realmfolk 期待生效。

## 稳定 ID 与资源目录

资产ID使用 `realmfolk:<type>/<name>`，例如 `realmfolk:body/sturdy`、`realmfolk:outer/academy`。小写ASCII、数字、下划线、路径分隔；不能使用中文路径、显示名或文件系统绝对路径作运行时ID。style/profession标签是选择偏好，不能拿标签字符串当资产存在证明。

建议将几何破坏性修改另发 `.../academy_v2`，或新增资产revision并保留旧内容；骨架拓扑或UV破坏性变化必须升级skeleton/UV版本。若包作者直接覆盖旧ID的纹理，程序保存ID不能神奇地恢复旧像素；因此发布流程必须保持旧ID语义/版本可用，并用资源哈希诊断不一致。

```text
asset_catalogs/realmfolk_appearance/v1/
  source/rig.json, uv_layout.json, poses.json
  source/components/*.json
  source/textures/*.png
  build/projects/{academy,steam,elven}_{standard,slender,sturdy}.bbmodel
  authoring/legacy/*.bbmodel  # 首轮工程原字节移存，不被日常构建覆盖
  authoring/                 # 作者另存工程；改动须人工回写canonical源
  draft/catalog.json, pools.json, resolved/*.json
  export/proposed/assets/realmfolk/appearance/models/<type>/<name>.rfmodel.json
  export/proposed/assets/realmfolk/appearance/textures/*.png
  preview/*.png, motion_*.gif
  tools/build_samples.py, init_samples.py, validate_samples.py, test_edit_rebuild.py
  build/build_manifest.json, build/verification.json
  verification/edit_rebuild.json, verification/edit_rebuild/
  PROVENANCE.md
```

未来客户端资源位于`assets/<namespace>/appearance/`。服务端默认/城市/职业池则在数据包`data/<namespace>/realmfolk/appearance/`或显式管理配置；不把全部高分辨率PNG塞进社会SavedData或每个实体同步数据。只有客户端资源包匹配才能显示自定义外观，这不意味着服务端可以执行模型文件中的脚本。

## catalog 条目

机器可读全例见实现仓 `draft/catalog.json`，25 ID均有来源与offline_prototype状态。模型条目以同一ID包含多个身体变体；无几何的皮肤/脸/眼仅引用图像层。

```json
{
  "id": "realmfolk:accessory/backpack",
  "type": "accessory",
  "model": "realmfolk:appearance/models/accessory/backpack.rfmodel.json",
  "texture": "realmfolk:appearance/textures/accessory_backpack.png",
  "materials": {
    "leather": {
      "texture": "realmfolk:appearance/textures/accessory_backpack__leather.png",
      "regionMask": "realmfolk:appearance/textures/accessory_backpack__leather_regions.png",
      "tintRegion": "leather"
    }
  },
  "supports": {
    "skeletons": ["realmfolk:humanoid_v1"],
    "bodies": ["standard", "slender", "sturdy"]
  },
  "occupies": ["back"],
  "styleTags": ["shared"],
  "professionTags": ["any"],
  "weight": 1,
  "colorRegions": ["cloth", "leather"],
  "excludes": [
    {"withSlot": "cape", "action": "reject"},
    {"withSlot": "hair_back_long", "action": "reject"}
  ],
  "hideRules": [
    {"poses": ["sit", "sleep"], "action": "hide_geometry", "restoreOnExit": true}
  ],
  "fallback": null,
  "status": "offline_prototype",
  "license": "GPL-3.0-or-later"
}
```

上例为了阅读省略cloth绑定，完整文件同时有cloth与leather。`fallback:null`在catalog专指可选资产缺失时省略，**不是**池继承时的null。`supports.bodies`使用身体变体名，解析成body资产的末段；`occupies`描述占位，base/outer是不同层；`excludes`任一侧匹配即冲突，无须双方重复声明。标签兼容条件使用withTag；槽使用withSlot。

贴图内分区红通道索引为skin1/cloth2/secondary3/trim4/leather5/metal6/lens7/hair8/eye9。身体皮肤与眼色独立；材质可绑定该区的快照颜色，不使用任意着色脚本。每个模型variant包含bone/from/to/uv/region，单位和坐标均由RFH1规范解释。

支持限制应严格：缺骨、未知身体、越界UV、重复ID、负/NaN权重、重复主槽、fallback环或路径逃逸均拒绝整批新目录，保留旧目录。建议限制首版每人≤96立方体、≤16个材质绑定、≤8件装饰；本轮最多48立方体、15绑定。绑定数不等于最终绘制调用数，可经合图/批处理收敛，再据实际游戏性能收紧。上述限额是拟议预算，不是已测帧率。

## 分层生成与确定性

1. **文明默认**：身体/发/耳/种族等独立人口池、服饰style、协调色板、基础槽默认权重；没有species设置则unspecified。建筑AA/SR/FS只为外观偏好提供标签，不推导生物种族。
2. **城市修正**：局部风格比例、移民/访客偏好、天气与劳动需求。用显式权重表达，例如学院服饰75%、蒸汽15%、精灵10%；这个比例仅示意，不改实际人口身份或访客名额。
3. **职业偏好**：给兼容资产乘权重、设置必需/禁用槽和附件预算。普通居民低装饰预算、常用短服；劳动者袖口清晰、少悬垂配饰、偏腰带/包；专业人物可用袍/帽/徽章。职业不改变肤色、种族和身体合法集合。
4. **个体抽取**：先身体/头，再皮肤/面部/眼/耳/发/须，再衣服/配件；按身体选择variant，筛互斥，最后统一选择色板与独立skin/hair/eye值。个体偏好可以保留原乡服饰，三风格可共城。
5. **关键人物覆盖**：用显式asset ID、颜色、variant、保留/清空槽掩码覆盖抽取结果，然后重新做完整兼容校验。冲突返回诊断，不能静默换掉指定帽或重抽外貌。关键人物不需要逐个普通居民设计。

草案合并：object递归覆盖、array整项替换、省略继承；null拒绝（catalog fallback与已解析的缺槽状态除外），空array表示明确不选。权重=基础weight×文明因子×城市因子×职业因子；有限正数，0表示排除，不允许最终必需池为空。城市提供的候选列表先完整校验，不在抽取时才忽略拼错ID。

种子建议按`SHA256(worldSeed|cityInstance|citizenUUID|appearanceVersion|slot)`派生**逐槽随机流**，候选ID排序后做累计权重抽取；保存所用算法版本，不能用Java/Python不稳定hash或共享全局随机流。每槽最多16次局部尝试，不无限拒绝重试。这个算法描述仍是提案，本轮九个resolved文件是人工定义的组合基准，**不是已实现随机人口模拟器的输出**。

冲突解决：身体与必需基础衣服优先，可选配饰不合法时尝试兼容候选再省略；不得因缺一个包重抽肤色/脸/身体。帽+发由低帽/低发、高发标签筛选；包+披风/垂尾互斥。固定人物指定冲突则拒绝发布，让作者修正。

配色从一组协调的cloth/secondary/trim/leather/metal/lens中选，不逐件任意随机RGB。skin/hair/eye独立。图案、轮廓、长短和结构仍承担主要差异，不能把5个棕色当5个外套资产。

## 保存、缺失与同步

建议在`Society.Citizen`加入`ResolvedAppearance`，首次生成人物时事务内解析并保存；数据应包含appearanceVersion、catalogRevision/manifestHash、skeleton、body、各槽**实际ID**、选中的几何variant、颜色hex实值、visualScale、presentation及species（若设定有）、关键人物锁定字段和生成来源。`draft/resolved/*.json`展示实际槽与colors；`palette`名称只是来源，不是重算颜色的依据。空beard槽显式保存为空。

加载世界先读快照；更改职业、迁居、发布新城市池、资源重载或重进世界都不重新抽取已经解析的脸、肤色、身体或衣服。以后换装由单独显式操作产生新的外观revision，保留生理外貌字段；关系已建立与否不作为自动换脸的借口。现有 refresh_unprotected 职业刷新不可隐式刷新外观。

旧存档无快照时一次性迁移：保留UUID、姓名、关系、床位、职业、库存和装备；由固定迁移版本/稳定ID解析并落盘。迁移前可继续显示旧村民renderer，不能每次接近NPC临时抽脸。实体NBT至少带CitizenId+外观revision/必要快照用于恢复；社会SavedData为主真值，避免两份快照相互覆盖。

缺资源时原始ID和参数仍保存在快照：可选附件按fallback链替代或省略；缺皮肤/基础衣服使用内置中性安全层；缺身体时整套按standard重解析**显示变体**，不能把sturdy外衣直接套standard。显示fallback单独缓存和报告，原文件恢复时可恢复原样；不覆盖持久化原ID，不借fallback重新随机。fallback无可用必需骨架时退回旧村民渲染并记录诊断。

服务端权威解析并保存；首次跟踪实体发送紧凑的resolved快照，变更发revision增量；资源包清单和哈希可在登录/重载时对齐。客户端不能决定NPC种族/职业/随机结果。模型PNG由资源包分发，不逐实体传输；无资源客户端使用显示替代。建议网络字段定长/限长，限制ID数量、颜色和scale范围，不接受客户端任意路径。当前协议3不能假定已支持新包；新增协议兼容策略需要正式实现。

## 程序工作清单与验收接口

| 新增能力（名称均为建议） | 要做什么 | 完成门槛 |
| --- | --- | --- |
| AppearanceCatalogLoader / ResourceReload | 解析RFH1、目录与材质；校验支持骨架/身体/ID/权重/互斥/fallback；原子替换；禁脚本和路径逃逸 | 错配置拒绝且旧目录继续；有缺失诊断 |
| AppearanceResolver | 文明→城市→职业→个体→关键人物；逐槽确定性流、冲突处理、预算和完整结果 | 顺序无关，强制互斥案例正确，有界失败 |
| ResolvedAppearance / migration | 社会SavedData事务、旧档一次迁移、ID和颜色实值、revision与锁定 | 重进/重载/换池不变脸，人物与经济状态不丢 |
| AppearanceSync | 登录/跟踪/变更同步、catalog hash与回退；服务端权威 | 多客户端一致、迟加入与重连一致、包体有界 |
| HumanoidCitizenModel / renderer | 注册自有layer或RFH1几何；13骨与身体rest，材质分层/cutout/cache；替换VillagerProfessionLayer与CrossedArmsItemLayer | 三体型正确，不再把村民职业层当新衣服 |
| AppearancePoseController | 复用sleep/isPassenger/isUsingItem/工作行为状态，站/走/坐/睡/持/食/工；肘膝与头部限制，变换顺序一致 | 四朝向、主副手、真实书/食物/工具正确，非靠交叉手臂假握持 |
| AttachmentRenderer | 挂点、体型变体、隐藏/恢复、真实装备遮挡、grip transform | 帽/发/镜/耳与包/袍/家具不严重穿插，隐藏不改库存 |
| BodyMetrics / facilities | 碰撞、眼高、乘坐接触、床头朝向和站起；导航门/步高检查 | 缩放与身体不使NPC卡门、陷椅、浮床，服务器判定一致 |
| appearance diagnostics / preview | 只读返回原ID、显示替代、variant、颜色、隐藏原因、revision与缺失；设计MCP只编辑偏好与关键人物覆盖 | 作者能查清为什么没有抽到/显示某资产 |
| 性能与发布门槛 | 纹理合成缓存按快照hash+资源revision共用；距离LOD/裁剪；透明排序、实际人口负载与显存测量 | 先以现有学院人数测基线再扩；未实测不得承诺256人性能 |

加载/保存/同步测试在实现时补充有意义的回归：字段未知、fallback环、缺资源恢复、map顺序独立、关键人物冲突、存档升级、两客户端、重进不变脸。本轮只有离线资产验证，不能把此表写成完成清单。
